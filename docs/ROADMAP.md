# 里程碑与验收

启动器 v2 按 M0 到 M5 推进。验收必须实测，不接受“编译通过”。设计约束见 [DESIGN.md](DESIGN.md)。

M0 的契约文件已冻结在 [contracts/](../contracts/README.md) 并推送到 `refactor/launcher-v2`。M0 剩余实施项以 `contracts/README.md` 的清单为准，本文件不重复。下表从 M1 开始。

## M1 环境引擎

主要内容：双根目录布局、预置 uv、托管 Python 装到 `data_root/runtime/python`、三来源依赖解析与 pinned snapshot、按实例建 venv。

验收：

1. 在没有 Python 的干净 Windows 上，从安装到三个模块 health 全部返回 200，全程不需要手工命令。
2. `currentUser` 与 `perMachine` 两种安装各跑一遍。程序根只读不写入，注册表没有新增 Python 项，数据根按用户隔离。
3. 篡改 pinned snapshot 时报错，不静默重建。
4. 断网重跑不重新下载。
5. 三个上游目录的 `git status` 保持干净。
6. 目录实例导入后，源码目录的 `git status` 也保持干净。

## M2 双源与包信任

主要内容：

- K5 签名 catalog，以及 GitHub 与 SourceForge 适配器。
- `files` 逐文件哈希、签名段附 `pubkey`、四级验签结果、原子安装与回滚。
- 公钥 TOFU、契约自检、多实例与 active 切换、旧版保留。
- 本地 zip 与目录导入。

验收：

1. 拔掉 GitHub 源，仍能从 SourceForge 装完。
2. zip 改一个字节时被拒，不留残留文件。
3. 两源 catalog 版本回退时被拒。
4. 已信任包删掉签名段后，不能被当成未验证包安装。catalog 的 `signature_required` 命中。
5. `pubkey` 验不过的包没有确认入口。
6. 未验证实例的确认框默认焦点在“取消”。
7. 未登记公钥的包显示完整指纹，按公钥未登记一级处理。
8. 指纹变更时阻断自动更新。
9. 同一 `module_id` 的两个实例并存，切换 active 是原子操作。切换失败时旧实例仍在运行。
10. 跨 variant 不比较版本。
11. `keep_versions=3` 时只留三版，pinned 实例不被清理，`data_dir` 不被删。
12. 契约不匹配的包标为“不兼容”。
13. 第三方模块卡片与安装确认框可见“非沙箱”文案。
14. 本地 zip 导入明示“无新鲜度锚、不自动更新”。首次导入填了期望指纹而不符时硬拒，不提供确认入口。
15. 目录导入不复制源码，固定按未验证处理，可由用户显式切为 active。
16. HEAD 变化时要求重新确认。启动器不执行任何 git 网络操作，卸载不删源码目录。

- 第 14 条：期望指纹硬拒已有断言，导入框缺少“无新鲜度锚”文案。
- 第 6、13 条只涉及 UI，留待 M4 界面。

app 侧命令面接线已由 M3 完成。真实两源网络、真实签名 catalog 分发与确认框仍属 M4 到 M5 范围。

## M3 生命周期重写

主要内容：按 role 拓扑启动、Job Object、异步健康检查、exit watcher、启动互斥、日志轮转、purge 顺序。

验收：

1. 强杀启动器后没有残留子进程。
2. 并发点两次启动，只起一个进程。
3. 实例崩溃 5 秒内 UI 变红。
4. 健康检查期间命令不被阻塞。
5. 第三方实例崩溃不影响官方实例。
6. 目录实例在源码变更被确认前不自动启动。

## M4 界面重做与管理页内嵌

主要内容：

- 首次向导、按 role 分组的模块卡片与实例列表。
- 环境与日志页、公钥与保留数设置。
- 同窗口子 WebView 与两个本地导入入口。

验收：

1. 新用户按向导完成“装完即聊”。
2. 模块 `/settings` 在启动器窗口内显示，随窗口缩放不脱版。
3. 连续切换多个实例的管理页不触发 Windows 建窗死锁，label 不撞。
4. 实例停止时显示占位页，不显示连接错误。
5. 子 WebView 创建失败时自动退化为独立窗口，不丢状态。
6. 横幅明确写出“启动器不存密钥”。
7. 七条真机 WebView 冒烟断言全部通过，清单见 [DESIGN.md](DESIGN.md) 的 7.6 节。
8. 离线时远程资源请求数为零。
9. 目录实例卡片常驻“本地源码·未验证”，导入确认框可勾选权限声明。

## M5 发布加固

主要内容：

- K1 与 K5 生成及内置、发布流水线、带外轮换预案。
- 双模式 NSIS 与 `embedBootstrapper`、三个产物、卸载钩子、体积预算。
- v1 本地状态处置、默认关闭的可选遥测。

验收：

1. 一次 release 同时产出 `setup.exe`、便携 exe 与 `SHA256SUMS`。三者版本一致，都过冒烟断言。
2. 安装包不超过 25 MB，便携 exe 不超过 15 MB。
3. 实测记录 `both` 索要 UAC 的时机，写进 README 与向导首屏。
4. 两种安装模式下，卸载后数据根清理干净，并询问是否保留用户数据。
5. 向导首屏明示首次下载量。
6. 检测到 v1 `modules-state.json` 时零导入、零删除。其 `linked` 指向的用户源码目录保持完好，提供“重新导入”入口并实测通过。
7. 两钥分离演练通过。K1 泄露时 K5 签的 `revoked` 生效；K5 泄露时 `expires` 窗口与强制升级路径成立。
8. 发布前置项逐项关闭，包括对外通知口径、两把密钥、签名工具与分发源。

2026-11-13 提前完成两把密钥的生成与内置。K1 签包，K5 签 catalog，私钥都离线保管在仓库外，公钥登记在 `keys/K1.json` 与 `keys/K5.json`，指纹写进 `state_v2.rs`。规程见 [SIGNING.md](SIGNING.md)。模块包确定托管在 SourceForge 的 `dounai-releases` 项目，打包与上传由发布方负责，SSH 认证与目录写入已实测通过。官方 catalog 尚未签发，发布流水线尚未开始，第 7、8 条验收保持未通过。真机安装与两源拉取也未实测。

## 顺序与推进方式

M0 与 M1 是地基。没有可复现的 Python 环境，包做得再好也跑不起来。M2 复用现有引擎，风险最低、见效最快。M3 改动最危险，放在有 UI 之前。M4 把 unstable 的真机风险集中验证。M5 的密钥与运维项不是代码，但必须并行启动，否则会再出现“引擎就绪、分发源没上线”。

在 `refactor/launcher-v2` 分支上按 M0 到 M5 分阶段提交，每阶段结束给作者一个可评审的边界。M5 完成前不合并 main。开工前先 `git fetch` 复核远端 HEAD。跨仓改动为零，分支评审只看一个仓。

## 实施期记录项

以下三项已给定约束，按约束直接写代码，不需要回到决策层，也不阻塞 M0：

## 残余风险与承接

面向用户的完整披露见 [SECURITY.md](../SECURITY.md)。下表只记验收覆盖不到的三条，以及各自的承接方式。

| 残余风险 | 承接方式 |
|---|---|
| 用户习惯性点确认 | 确认框展示完整指纹与权限清单，默认焦点在“取消”。指纹变更阻断自动更新。无法根除，UI 文案要明说 |
| 首次本地导入没有新鲜度锚 | 可选期望指纹覆盖“用户知道指纹”的场景。用户不知道指纹时仍有窗口，导入框必须明示 |
| 第三方界面仿冒配置页 | `explicit_only`、常驻发布者标记、确认文案披露与手动回退。启动器无法验证界面内容，不得写成“已验证” |

契约文件的变更规则见 [contracts/README.md](../contracts/README.md)。

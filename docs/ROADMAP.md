# 里程碑与验收

启动器 v2 按 M0 起的里程碑推进，编号按范围定、不按时间。验收必须实测，不接受“编译通过”。设计约束见 [DESIGN.md](DESIGN.md)。

M0 的契约文件已冻结在 [contracts/](../contracts/README.md) 并推送到 `refactor/launcher-v2`。M0 剩余实施项以 `contracts/README.md` 的清单为准，本文件不重复。下表从 M1 开始。

## M1 环境引擎

主要内容：双根目录布局、预置 uv、托管 Python 装到 `data_root/runtime/python`、三来源依赖解析与 pinned snapshot、按实例建 venv。

验收：

1. 在没有 Python 的干净 Windows 上，从安装到三个模块 health 全部返回 200，全程不需要手工命令。
2. `currentUser` 与 `perMachine` 两种安装各跑一遍。程序根只读不写入，注册表没有新增 Python 项，数据根按用户隔离。
3. 篡改 pinned snapshot 时报错，不静默重建。
4. 断网重跑不重新下载。
5. 三个上游目录的 `git status` 保持干净。
6. 目录实例导入后，源码目录的 `git status` 也保持干净。
7. 删掉 `state/install.json` 后重启启动器，能自己补齐，装依赖不再报 `os error 2`。
8. 程序根有 `bin/uv.exe` 时，断网也能建 venv 并完成依赖准备，不尝试下载 uv。

### 收口项（2026-11-13 复核发现）

M1 被当作已落地，但有两处其实没接上，表现为「模块能装、依赖永远装不上」：

- **`state/install.json` 从来没有被写出来。** 它按设计由安装器（M5）写一次，而 M5 未开始，启动器也不兜底，于是 `prepare_instance_env` 一读就 `os error 2`。语义要扩一条：安装器优先写，启动器在缺失时自举补写（用内置 uv 的路径、版本与 sha256 调 `InstallState::initialize`）。
- **`bin/uv.exe` 不在包里。** 环境引擎从 GitHub release 下载 uv，而目标机器连不上 GitHub（实测 21 秒超时），所以「允许联网补齐」这条路也是死的。改法：从 PyPI 镜像取 `uv-0.13.7-py3-none-win_amd64.whl`，解出 `uv.exe` 钉 sha256 并入包；下载分支保留为兜底，并把下载源从 GitHub 改成可配置镜像。

另有一条使用面修正：首次「安装依赖」默认离线，而首次装依赖必然拉包，等于按钮天生不可用。默认放行联网，离线作为重试选项。

**进度（2026-11-13 19:55）**：三条都已落地，第 7、8 条验收由单测与集成测试覆盖（`tests/bundled_uv.rs` 走生产代码：`AppStateV2::new` 补写 → `locate_uv` 命中随包文件 → `uv --version` 真跑通，全程禁止联网）。

- `InstallState::ensure` 四种情况：缺失则新建；一致则不写盘；只差 uv 三元组则只改三元组；读不出来或两个根不一致则先备份 `install.json.bak` 再重写。设置页「install.json」一行显示补写原因。
- uv 0.13.7 从阿里云 PyPI 的 wheel 取，钉 `sha256:1791d7a9…` 与 31 803 184 字节。三段落地：`scripts/fetch-uv.py` → `build.rs` 复制到 `target/<profile>/bin/` → `bundle.resources` 落到 `$INSTDIR/bin/`，因此开发、直接跑 release exe、装机三种方式走同一条候选路径。二进制不入库。
- 补齐顺序改成 GitHub 优先、PyPI 镜像兜底（`UV_DOWNLOAD_URLS`）。
- 首次装依赖默认联网，模块菜单保留「安装依赖（离线）」。

体积实测（2026-11-13 19:55，`cargo tauri build`）：NSIS 安装包 **13.33 MiB**，上一版 2.98 MiB，即内置 uv 带来 +10.35 MiB，仍在 25 MB 预算内。NSIS 脚本确认落点为 `$INSTDIR\bin\uv.exe`（安装时写入、卸载时删除），与 `Paths::bundled_uv_path()` 一致。

顺带发现一条不属于本里程碑的问题：这次构建的 NSIS 把 `pack.exe`（774 KB）与 `sign_catalog.exe`（357 KB）也装进了用户机器——它们是发布工具，不该随客户端分发。原因待查（两者都是本 crate 的 `[[bin]]`，bundler 把它们当 sidecar 收走了）。记在 M5 打包项处理，M1 不动。

### 返修：pinned 快照口径与安装进度（2026-11-13 20:00）

真机报 `SnapshotMismatch: zip 实例缺少 manifest.runtime.snapshot_sha256`。三个已发布包的 `manifest.runtime` 都没有这个字段，按旧口径「缺字段即硬拒」等于所有在线包装不了依赖。

- **口径改为**：声明了就必须一致（不符仍硬拒，那是篡改信号）；没声明则放行，记 `runtime.json` 的 `snapshot_pinned = false`，界面标「快照未锚定」。依据是 `kind = uv_lock` 的锚点本来就是签名包内那份 `uv.lock`，同步前还会再比对一次；发布者重复写哈希没有增量保证。
- **安装进度**：模块卡片上的实例行新增一行进度（六阶段 + 明细 + 细进度条）。引擎侧走线程本接收器旁路上报，`uv -v` 的包名行流式转发；前端只改那一行 DOM。不做百分比，uv 没有可依赖的「已装 N 个」接口。

细节与门禁数字见 [TESTING.md](TESTING.md) 同节。

### 返修：启动即退出与「没有停止按钮」（2026-11-13 21:15）

真机：OmniNexus 与 MoodVoice 点启动后几秒内退出（`exited code=3`），再点启动被回「进程还在运行，但健康检查没通过，先点停止」，而界面只有「启动」。三处原因叠加：

- **包自身没装进 venv。** 引擎同步依赖带 `--no-install-project`，三个包都是 `src/<pkg>` 布局，`python -m <pkg>` 直接 `No module named` 退出。启动器现在把包根的 `src/` 前置进 `PYTHONPATH`，manifest 自带的 `PYTHONPATH` 保留在后面。手动验证：三个包在补路径后 health 全部 200。
- **备用端口全撞 18101。** 单实例启动把「一个实例」当整表算端口，每个非 active 实例都分到 `18101`，后启动的绑不上端口退出。端口分配改为统一按整张已登记实例表算，单启、一键启、视图三处一致。
- **死进程句柄不清。** watcher 只更新状态不摘进程表，`owns()` 恒为真；而快照已把 `pid` 清空，界面只给「启动」，于是用户被卡在「先点停止」却没有停止按钮。`owns()` 改用 `try_wait` 复核存活并就地摘掉死句柄，`stop` 先看存活，一键停止额外收掉「判超时但进程还活着」的实例；探测线程在进程退出后立即收工，不再空跑满 90 秒预算。

细节与门禁数字见 [TESTING.md](TESTING.md) 同节。

### 返修：active 槽自动补位（2026-11-13 21:35）

三处启动问题修好后暴露出更基础的一条：真机 `installed.json` 的 `active` 是 `{}`，三个模块全落在 `18101-18103` 备用端口段，而组装层只认 8101、8102、8103——界面一切正常，链路一条都连不上。

- **安装即上位**：装完若该 role 的槽还空着，把刚装的实例设为 active，`InstallResponse.activated` 回传实例 ID，安装提示里写「已设为该角色的主实例」。
- **导入目录同样上位**：用户亲手指定的目录等于一次显式指名，因此恒为 C 类的 dir 实例也允许；C 类签名包不享受这一条——对它的确认针对「安装」，不是「让它接管链路」。
- **卸载后补位**：卸掉的若是 active，按 `instance_id` 字典序补一个同 role 的实例。
- **启动时自愈**：`heal_active_slots` 对 `input`/`llm`/`output` 各扫一次，把老版本装出来的空槽修好，不必重装。

槽已占用时新实例不动槽位，退居备用实例，由用户在卡片菜单里切。规则表见 [contracts/README.md](../contracts/README.md)，机械细节见 [DESIGN.md](DESIGN.md) 第 7 章。

### 返修：启动被判超时与重复启动（2026-11-13 20:20）

真机点一次「启动」，日志里出现四行 `start`、一个 `spawned`、三个「实例已在启动中」；六秒后探测报 `health=Unhealthy contract=Unhealthy`，再点一次则提示「已在外部运行」，而 health 其实已是 200。

- **重复启动是前端问题**：`bindActions` 每次重绘都往常驻容器上 `addEventListener`，N 次刷新后一次点击触发 N 个处理函数。改成幂等绑定（WeakMap 存 action 表，监听器只挂一个），并按实例加在途标记，一键启停共用闸门。
- **超时是预算口径问题**：探测预算原是固定 4 秒，而 Python 冷启动要十几秒。改用 roles 的 `startup_timeout_ms`（60/90 秒），探测间隔前 5 秒 50 ms、之后 400 ms。
- **失败语义**：预算用尽不再清 `pid`，改记「启动超时·进程仍在运行」并保留停止入口；再点启动时若自己的进程已健康，`mark_recovered` 收回 `running`，不再拉起第二个；`mark_external` 加守卫，自己持有的进程永不标成「外部启动」。

细节与门禁数字见 [TESTING.md](TESTING.md) 同节。

## M2 双源与包信任

主要内容：

- K5 签名 catalog，以及 GitHub 与 SourceForge 适配器。
- `files` 逐文件哈希、签名段附 `pubkey`、四级验签结果、原子安装与回滚。
- 公钥 TOFU、契约自检、多实例与 active 切换、旧版保留。
- 本地 zip 与目录导入。

验收：

1. 拔掉 GitHub 源，仍能从 SourceForge 装完。
2. zip 改一个字节时被拒，不留残留文件。
3. 两源 catalog 版本回退时被拒。
4. 已信任包删掉签名段后，不能被当成未验证包安装。catalog 的 `signature_required` 命中。
5. `pubkey` 验不过的包没有确认入口。
6. 未验证实例的确认框默认焦点在“取消”。
7. 未登记公钥的包显示完整指纹，按公钥未登记一级处理。
8. 指纹变更时阻断自动更新。
9. 同一 `module_id` 的两个实例并存，切换 active 是原子操作。切换失败时旧实例仍在运行。
10. 跨 variant 不比较版本。
11. `keep_versions=3` 时只留三版，pinned 实例不被清理，`data_dir` 不被删。
12. 契约不匹配的包标为“不兼容”。
13. 第三方模块卡片与安装确认框可见“非沙箱”文案。
14. 本地 zip 导入明示“无新鲜度锚、不自动更新”。首次导入填了期望指纹而不符时硬拒，不提供确认入口。
15. 目录导入不复制源码，固定按未验证处理，可由用户显式切为 active。
16. HEAD 变化时要求重新确认。启动器不执行任何 git 网络操作，卸载不删源码目录。

进度（2026-11-13）：主界面已重写，六个视图（模块、环境、日志、管理、设置、导入本地）与深浅双主题落地，按 role 分组、实例行、外部启动标记、未验证标记都已接线。原「套装」视图已删除：它按 v1 的 `module_id` 列表规划安装，与 v2 的 `module_id@variant` 安装单位对不上，页面上的「开始安装」从未接通；在线安装当时改到模块页的「模块目录」弹窗，M8 起独立成侧栏「下载」视图。入门引导、日志页重排与内嵌子 WebView 三项剩余工作均已实现，见下面各节。真机验收仍待实测（七条 WebView 冒烟断言与逐条点选）。

同窗口子 WebView 已于 2026-11-13 完成，处置如下：

- `core/src/admin_host.rs` 这份 M0 冻结契约第一次有了消费者：`admin_embed.rs::TauriAdminHost` 实现 mount / unmount / reload，resize 与 visible 不进 trait（它们没有生命周期语义，不该为改动冻结契约）。
- 主窗口保留自己的 WebView，管理页是 `Window::add_child` 挂上来的原生子视图，覆盖「管理」视图里 `#admin-slot` 的坐标。原设计的「无 WebView 壳 + 主 UI 也是子 WebView」没有采用：那要重写窗口定义与 capability 适配，收益只是形态更统一。理由写在 [DESIGN.md](DESIGN.md) 的 7.7。
- **顺手修掉一处安全回归**：capability 原本是 `windows: ["main"]`，而 Tauri 的 ACL 判定是「webview label 或 window label 任一匹配」，内嵌页挂在 `main` 窗口下会继承主窗口全部命令权限。现改为 `webviews: ["main"]`，内嵌页与独立窗口都不匹配；两条路径共用一份全 frame 注入清理脚本。
- URL 仍只由 Rust 从 manifest 与端口表拼出；子 WebView 另有 `on_navigation` 限制同 host 同端口。label 按 `instance_id` 派生，重复点击复用；创建在独立线程里跑，避免 Windows 上 Webview2 的 COM 死锁。
- 生命周期绑定进程状态：未启动显示本地占位页、health 转健康 reload 一次、进程退出隐藏并回占位、卸载时销毁、切视图时 hide 而非 close（保住填了一半的表单）。创建失败自动退化为独立窗口，不丢状态；`web_ui.embed = false` 按模块声明走独立窗口。
- 坐标由 `clampAdminBounds` 夹进可见视口，窗口缩放 120ms 一拍重下发；6 项前端单测 + 3 项 Rust 单测。
- **真机首测发现并修复（2026-11-13）**：`admin_host::validate_mount_request` 原要求 URL 路径非空，而 `dounai-input` / `moodvoice` 的 `web_ui.path` 是 `/`，拼出 `http://127.0.0.1:8101/` 被误判「缺少路径」，内嵌直接降级成独立窗口（用户截图确认降级路径本身可用）。现放行根路径、只挡 `..`，新增遍历三个官方样例 manifest 的 Rust 回归测试与宿主层用例。此前单测只用了 OmniNexus 的 `/settings`，门禁全绿也没抓到——这是「契约样例与宿主校验」缺一致性测试，不是编译能发现的问题。
- 验收 2 到 5 实现完成；真机首测已看到降级路径生效，根路径修复后内嵌是否成功待复测；连续切换、缩放与验收 7 的七条冒烟断言全部待真机。

入门引导已于 2026-11-13 完成，形态在实现后改过一次：

- 第一版是四屏向导（本机现状 → 选模块 → 装依赖 → 完成），被否掉了：它把「配置」和「上手」拆成前后两段，用户必须按顺序走完才能用主界面，而装依赖可能要几分钟。

## M6 编排：链路

> 编号按范围定，不按时间。M6 与 M7 的实现顺序排在 M5 之前，见“顺序与推进方式”。

主要内容：新增一种用户自定义对象 **链路**（Chain），由若干实例按顺序组成，一键启动整条链路。它只编排、不安装，也不复制 `installed.json` 里的任何事实。

- 数据模型：`state/chains.json`，`schema_version: 1`，每条链路 `{ id, name, steps[], created_at, updated_at }`。`steps` 存 `instance_id` 而不是 `module_id`——同一模块可以有 primary 与 standby 两个实例，链路必须指到具体那一个。契约文件 `contracts/chains-v1.schema.json` 连同样例与 `validate.mjs` 断言一起加，不动 M0 已冻结的既有 schema。
- 命令面：`list_chains`、`save_chain`、`delete_chain`、`start_chain`、`stop_chain`。全部异步，启动在阻塞池里跑。
- 启动语义：串行。每步按该实例已有的健康与契约门禁等结果，通过再下一步；任一步 failed 或超时即中止，报出「第几步、哪个实例、什么原因」。已启动的实例不回滚，另给「回滚停止」按逆序停。
- 停止语义：逆序停，单步失败不阻断后续。
- 悬空引用：实例卸载后链路保留原值，卡片标「缺 1 项」，不静默改写用户数据。
- 界面：导航第二项，卡片列出步骤与各自状态点，主按钮为一键启动与停止，编辑走模态（名称、勾选实例、上下移排序）。

验收：

1. 三个实例组成一条链路，一键启动后按声明顺序全部 running，界面上能看出当前在第几步。
2. 把链路中间一步的端口占掉再启动，停在那一步并说明原因，前后实例状态与实际进程一致。
3. 链路里有一个未装依赖的实例，启动前统一提示并支持一键补装，不在中途崩。
4. 删除链路中的一个实例后，卡片显示「缺 N 项」，启动时拒绝并指出是哪一项。
5. 停止按逆序执行，单步失败不影响其余步骤继续停。
6. `chains.json` 通过契约校验，手改出非法 id、空 steps 或重复项时被拒。

## M7 资源占用监控

主要内容：按实例给出 CPU、内存与进程数，2 秒采样，只在内存里留 60 点，不落盘。

- 数据源走 Job Object，不靠 parent-pid 猜进程树：一个实例本来就有独立 Job（M3 强杀兜底用），`JobObjectBasicProcessIdList` 列出的就是整棵进程树，含孙子进程；对每个 pid 用 `GetProcessTimes` 差分算 CPU、`GetProcessMemoryInfo` 取工作集后求和。
- 命令面：`instance_usage`，只读内存快照，不发 HTTP、不碰磁盘。
- 界面：模块卡片状态行加「内存 · CPU」，环境页加运行中实例表（按内存排序、含进程数），状态栏显示合计。外部启动的实例没有 Job，退回按 pid 单进程采样，取不到就显示 `—`，不显示 0。

验收：

1. 启动一个实例后 5 秒内卡片出现非零内存，CPU 数值随负载变化。
2. 实例拉起子进程时，内存与进程数随之上升（证明统计的是进程树而不是单个 pid）。
3. 停止实例后数值归零，不残留上一轮读数。
4. 外部启动的实例显示 `—` 而不是 0，且不因此报错。
5. 关闭窗口或长时间空闲时采样线程不占 CPU（无实例运行时不采样）。

### 为什么「加源」必须同时「加公钥并信任」

这一节写的是 M8 落地前的判断依据：M8 之前的 `refresh_catalog` 对任何 URL 都用**内置 K5** 验签，`allowed_hosts()` 也只含 GitHub 与 SourceForge 后缀。多源时三条路都不通：

1. 社区源用自己的钥匙签 catalog → 内置 K5 验不过，源直接不可用。
2. 想验过就得共用官方 K5 私钥 → 等于把官方的新鲜度锚交给第三方。
3. 干脆不签 catalog → `sequence` 单调、`expires`、`revoked` 全丢，退回 v1 的自证局面。

因此添加源是一次原子操作，不是「填个 URL」：URL + 公钥（粘贴 base64 或导入文件）→ 展示完整 SHA-256 指纹 → 确认框默认焦点在「取消」→ 公钥写入 `state/sources.json` 的源条目并绑定该指纹 → 该源启用。验签公钥来自**本地注册表**，不采信 catalog 自述的 `signature.pubkey`；未登记公钥签的 catalog 一律硬拒，不提供「仍然继续」。

**这把公钥不能进包信任表**。`KeyPurpose` 枚举已存在，但只挂在 `BuiltinKey` 上；用户登记的 `TrustedKey` 没有用途字段，而 `is_trusted(fp)` 同时查 `builtin` 与 `trusted`、完全不看 purpose。若把社区源的 catalog 公钥按现有 `confirm_trusted_key`（走 `tofu()`、固定写 `origin = tofu`）写进 `state/trust.json`，同一个指纹会命中包判定的 A 类「已信任发布者」，等于给用户信任一个下载位置的同时，顺手信任了该发布者签的任意模块包。M8 必须让「签 catalog 的钥匙」与「签包的钥匙」在存储与判定上隔离，形状见「已拍板」第 4 条。顺带发现：内置 K5 是 `catalog_signing`，却也在 `is_trusted` 的查询表里，理论上签包同样能判 A 类；K5 私钥离线保管且不用于签包，M8 不动这条判定链，只记为已知限制。

其余不变式沿用 M2：`trust.rs` 的信任单位是公钥而非 URL；内置源 `deletable: false`、可禁用不可删；撤销公钥立即停用该源，已装实例不卸载但禁止自动更新并标「发布者已不再受信任」；重定向逐跳校验域名沿用 `m2_http.rs`，每个源的 host 白名单独立，不给「任意 https URL 都能拉」的空白名单。官方 K5 继续只用于官方两源，社区源不复用它。

### 多源裁决与版本展示

- 官方主源与其镜像仍是「同一份 catalog 的两个副本」，继续按 `sequence` 与新鲜度二选一；**不同发布者的源是并列集合**，不能互相覆盖。合并条目按 `source_id / publisher_fp / module_id / variant` 区分，重名时界面显示来源与发布者指纹，安装目标由用户点选的那一行决定，不做隐式优选。
- 每个源独立记 `sequence` / `expires` / `last_seen_version`，否则社区源的 sequence 能压制官方源，或一方的回退状态污染另一方。「跨 variant 不比较版本」（M2 验收 10）在新界面上继续成立。
- `catalog-v2.schema.json` 已经带 `variant` / `version` / `min_version` / `revoked` / `sources[]` / `expected_signer_fp`，缺的是后端 `CatalogEntryView` 把字段补全（原来 `download_url` 只取 `sources[0]`）和前端的分组视图。新增的只有源注册表状态 schema，按 [contracts/README.md](../contracts/README.md) 的变更规则走，`validate.mjs` 必须加负例。

**契约在 M8 期间改过三处，与本节原计划「不改 M0 冻结文件」不同**：多源场景下那三处不改就写不出正确实现，事后擦屁股比提前改更贵。

| 文件 | 改动 | 为什么非改不可 |
|---|---|---|
| `catalog-v2.schema.json` | `signature.signer_fp` 改为必填；`key_id` 降级为展示字段 | 跨源时必须知道「这份目录该由哪把钥匙验」。`key_id` 只是人写的标签，不能当判定依据 |
| `source-v1.schema.json` | instance 增 `source_id`；停用 `catalog_state.sequence` / `expires` | 实例要记来源，否则跨源同名实例分不清是谁；`sequence` / `expires` 是目录级水位，多源下必须下沉到源表 |
| `sources-v1.schema.json` | 新增 | 源注册表与每源新鲜度状态 |

教训记在这里：契约冻结如果发生在「还没想清楚要支持什么」的时候，后面每一处妥协都要在实现里擦一遍屁股。M8 的三条拍板（源表独立、跨源并存、catalog 公钥隔离）反过来要求契约能改，所以这几处就改了，没有加兼容分支。

2. **跨源同名 `module_id@variant` 允许并存，active 只在用户点「设为当前」时才变**。`active[role]` 本来就绑 `instance_id`，并存没有技术障碍（此前记的「两者会争同一个 active 槽」不准确，已更正）。安装确认框必须显示来源名与发布者指纹，界面标「跨源同名」，不做隐式优选、不自动激活。
3. **社区源实例默认 `auto_update: false`，只提示有新版、不自动装**。复用 `source-v1` 现有字段与「C 类固定 false」先例，零契约改动；跨源自动更新一律禁止。
4. **另立源公钥表，物理隔离**。catalog 签名公钥存在 `sources.json` 的源条目里，验 catalog 只查这张表；`state/trust.json`、`TrustedKey` 与 `is_trusted()` 零改动，判定代码根本读不到这把钥匙。代价是留下上面那条 K5 理论越权，按已知限制披露，不在 M8 里动 M2 判定链。

由此产生的实施约束：新状态文件必须自带 schema 与 `validate.mjs` 正负例；验签公钥只来自本地源表，不采信 catalog 自述；添加源与撤销源的整个流程中 `trust.json` 不应产生任何写入（验收 3、12 据此实测）。

### 不在范围

不做源内搜索 / 评分 / 评论，不从官方源自动发现社区源（源列表只能用户自己加），不做「一键信任」或「跳过验签」开关，不改 K1 / K5 的官方轮换路径，不因此改动本地 zip 与目录导入的未验证口径。

验收：

1. 侧栏「下载」是独立视图而不是模态；切换视图回来不丢筛选条件，装包时主界面仍可操作。
2. 填一个未登记公钥的源 URL，拉取被拒并写明原因，界面没有「仍然继续 / 跳过验签」按钮。
3. 添加源必须走「URL + 公钥 + 完整指纹 + 确认框（默认焦点在取消）」；取消后 `sources.json` 没有残留，`trust.json` 全程零写入。
4. 用该源登记公钥签的 catalog 能装；换成另一把钥匙签的同内容 catalog 被拒，不落盘、不进会话缓存。
5. 撤销公钥后该源立即停用，已装实例不卸载、不被自动更新，界面标「发布者已不再受信任」。
6. 内置官方源可禁用、不可删除；禁用后本地 zip 导入仍可用。
7. 两个源同时启用时条目并列且各自标来源；禁用社区源后其条目消失，官方条目与已装实例不受影响。
8. 同一 `module_id` 的多个 variant 与多个 version 能同时看见；选旧版本安装时被 `last_seen_version` / `min_version` 拦下并说明，M2 验收 3、10 在新界面上仍成立。
9. 官方源与社区源的 sequence 各自单调：社区源把 sequence 调到 9999 不影响官方源裁决，官方源 catalog 回退仍被拒。
10. 离线时远程请求数为零；「允许访问的域名」只列已启用源的 host，不是全局放开。
11. `validate.mjs` 新增负例断言：源条目缺 fingerprint、内置源 `deletable: true`、catalog 自述 pubkey 被采信，三者都被拒。
12. 为社区源登记的 catalog 公钥只进 `sources.json`，不能让用同一把钥匙签的模块包被判为 A 类「已信任发布者」；`trust.json` 不出现该指纹，包仍按 M2 四级判定走，需要确认的必须弹确认框。

## 顺序与推进方式

M0 与 M1 是地基。没有可复现的 Python 环境，包做得再好也跑不起来。M2 复用现有引擎，风险最低、见效最快。M3 改动最危险，放在有 UI 之前。M4 把 unstable 的真机风险集中验证。M5 的密钥与运维项不是代码，但必须并行启动，否则会再出现“引擎就绪、分发源没上线”。

实现顺序（2026-11-13 重排）：

```
M1 收口（install.json 自举 + 内置 uv）
  → M4 收口（日志页重排 → 入门引导 → 内嵌子 WebView，三项已实现、真机待验）
  → M8 下载中心与可配置源
  → M6 链路
  → M7 资源占用
  → M5 发布加固（含实测后的体积预算重定）
```

排法依据：

- **M1 收口在最前**，因为它是唯一一条会让「模块装好了却永远装不上依赖」的死结，后面每个里程碑的真机验收都要靠它才能跑起来。
- **日志页排在 M4 三个剩余项的最前**，因为后面每一步排障都要读日志；入门引导与内嵌 WebView 依赖真机交互，放在同一里程碑的后半段。
- **M8 紧接 M4**：它和 M4 同属界面工作，要新增侧栏视图，跟在「内嵌子 WebView」之后共用一轮真机验证。更硬的理由是它改写 7.2 的源公钥口径与 [SECURITY.md](SECURITY.md) 的对外披露，而 M5 验收 8 的「对外通知口径」必须基于新模型定稿——放到 M5 之后写，那份披露要返工。与 M6 / M7 无依赖，排在前面还能让 M6「多个实例一起跑」的验收顺带覆盖多源装出来的实例。
- **M6 早于 M7**：监控的意义建立在「多个实例一起跑」之上，链路先给出那个场景。
- **M5 放最后**，它要收紧体积预算与产物数量，必须在功能冻结之后做；内置 `uv.exe` 的体积增量也在那时按实测重定。M8 属于功能面，必须赶在冻结前完成。

在 `refactor/launcher-v2` 分支上按上述顺序分阶段提交，每阶段结束给作者一个可评审的边界。M5 完成前不合并 main。开工前先 `git fetch` 复核远端 HEAD。launcher 仓内跨仓改动为零，分支评审只看一个仓。

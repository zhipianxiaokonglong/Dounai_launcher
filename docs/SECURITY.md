# 安全策略

本文件适用于 Dounai 启动器。

## 报告漏洞

不要在公开 Issue 中披露细节。使用仓库的安全公告入口提交：
<https://github.com/zhipianxiaokonglong/Dounai_launcher/security/advisories/new>

入口不可用时，开一个不含技术细节的 Issue，说明需要安全联系方式。

报告须包含五项：受影响版本的 commit hash、运行环境、最小复现步骤、影响范围、可选的概念验证。不要附带真实密钥、对话内容或用户数据。

## 响应时限

| 等级 | CVSS（通用漏洞评分系统） | 响应 | 修复目标 |
|---|---|---|---|
| Critical | ≥ 9.0 | 24 小时 | ≤ 7 天 |
| High | 7.0 – 8.9 | 72 小时 | ≤ 14 天 |
| Medium | 4.0 – 6.9 | 7 天 | 下一版本 |
| Low | < 4.0 | 14 天 | 不设修复期限，随下一次常规发布处理 |

Critical 与 High 未修复时不得发布。

## 安全边界

启动器执行本机命令、解压外部包、按 manifest 决定入口与权限。这三件事决定本仓库的安全门槛高于普通模块。

v2 的信任模型分四步：

1. 每个 zip 包的 manifest 自带 32 字节 Ed25519 公钥与 `files` 清单。启动器先用包内公钥验签，再按公钥的 SHA-256 指纹查信任列表。
2. 验签结果分四级：已信任、公钥未登记、未签名、验不通。前两级可安装，第三级需单次确认并常驻标记，第四级硬拒。
3. K1（包签名公钥）签官方包，K5（catalog 签名公钥）签官方 catalog 与新鲜度元数据。两钥分离，任一把泄露都需带外公告与强制升级启动器。
4. 目录与 Git 仓库导入固定按未验证处理。源码随时可变，`files` 清单不适用，启动器不承诺入口哈希。

公钥未登记与未签名两级的确认不能做成可常开的设置项。

### 第三方下载源

「下载」页允许用户添加社区源。信任一个**下载位置**与信任一个**发布者**是两件事，两者在存储与判定上必须分开，否则「我信这个下载位置」会悄悄变成「我信这个发布者签的任意包」。

| | catalog 签名公钥 | 包签名公钥 |
|---|---|---|
| 存储位置 | `state/sources.json` 的源条目 | `state/trust.json` |
| 判定入口 | 验 catalog 时只查源表 | 包验签后查 `is_trusted()` |
| 撤销方式 | 撤销该源：立即停用，不卸载已装实例，禁自动更新 | 撤销发布者：包退回 B/C 类判定 |
| 能否影响对方 | 不能。源的 catalog 公钥不会让同钥匙签的包判为 A 类 | 不能。包信任表不影响任何源的 catalog 验签 |

具体口径：

- 验 catalog 的公钥只来自本地源注册表，**不采信 catalog 自述的 `signature.pubkey`**。未登记公钥签的 catalog 一律硬拒，界面没有「仍然继续 / 跳过验签」。
- 添加源要展示完整 SHA-256 指纹并显式确认，默认焦点在「取消」。整个添加与撤销流程对 `trust.json` 零写入。
- 官方 K5 只服务官方源，社区源不复用它，也不共用官方私钥。
- 每个源有自己的域名白名单，出网白名单由已启用源逐个派生，没有全局兜底列表；白名单为空即不发起任何远程请求。
- 撤销源的公钥后该源立即停用。已装实例不卸载、不自动更新，界面标「发布者已不再受信任」。
- 会话级 catalog URL 已删除。它能从白名单外的主机拉目录，绕过按源验签。

已知限制见下表：内置 K5 标着 `catalog_signing`，却也在包信任的查询表里。

### 泄露后的对外通知口径

| 泄露 | 用户要做什么 | 要不要升级启动器 |
|---|---|---|
| 官方 K5（catalog） | 等 `expires`（不超过 7 天）窗口过去，或公告后升级启动器换内置公钥 | 要 |
| 官方 K1（包） | 公告 + 升级启动器；旧 K1 签的包由新版 catalog 的 `revoked` 列表撤掉 | 要 |
| 某个社区源的 catalog 公钥 | 在「下载」页撤销该源：立即停用、已装实例标「发布者已不再受信任」 | 不要 |

社区源这一行是 M8 带出来的新口径：源的公钥不是内置的，用户自己登记、自己撤销，所以泄露后的处置动作在用户手里，不需要发新版。**但这不等于用户一定会发现**——启动器没有「这个源我见过异常」的提示，撤销动作得由用户自己发起或由社区公告提醒。

## 防线

以下前四条在 v1 已有，v2 继续保留；第五条随上游修复移植：

1. 解压前逐条校验路径。绝对路径、UNC 路径、`..` 组件与 Windows 保留设备名一律整体拒绝。任一条目危险时，整个安装失败。
2. 安装先写临时目录，全部成功后原子替换。覆盖旧版先备份，失败自动还原。
3. 下载内容按 SHA-256 校验，失败时删除临时文件。
4. 上游进程的 stdout 与 stderr 默认丢弃，不写入日志。上游输出可能含对话内容。显式设置 `DOUNAI_LOG_CHILD_OUTPUT=1` 后才会按行写入实例日志，这是用户自担的选择；启动器自身事件（拉起、退出码、探测结果）始终记录并按大小轮转。
5. 外部管理窗口在页面脚本执行前逐帧清除 Tauri 的全局注入对象。capabilities 把命令权限限定在主窗口，ACL 仍是防线；清注入只减少可试探的入口，不替代 ACL，也不承诺页面无法从其它指纹判断宿主。

## 已知限制

| 限制 | 说明 |
|---|---|
| 未签名与公钥未登记的包依赖用户判断 | 确认框展示完整指纹与权限清单，习惯性点确认无法根除 |
| 第三方界面可仿冒配置页 | `shell` 允许第三方填槽。启动器不向界面注入密钥，也没有从界面调用管理命令的通道，但无法验证界面内容 |
| 目录实例完整性不可验证 | 固定未验证、变更重新确认、不自动更新、不自动激活 |
| 第三方模块拥有运行用户的全部权限 | 本版不做进程沙箱。M3 的 Job Object 只负责在启动器退出时终止子进程树 |
| 官方 catalog 尚未签发 | K5 已内置真实公钥，但 SourceForge 上还没有签名 catalog；远程分发按不可用处理，不降级为未签名放行 |
| 内置 K5 同时出现在包信任表里 | K5 标着 `catalog_signing`，但 `is_trusted()` 不看 `purpose`，理论上同一把钥匙签的包也会判 A 类。K5 私钥离线保管且不用于签包。属 M2 判定链，M8 未动 |
| 社区源的 catalog 公钥由用户带外取得 | 启动器只能验「这份目录是这把钥匙签的」，无法判断这把钥匙是否值得信。指纹展示与显式确认是唯一的把关点 |
| K1 与 K5 私钥都没有口令或硬件保护 | 文件只靠仓库外目录与 ACL 保护。拿到 K1 即可签发已信任的包，拿到 K5 即可伪造索引 |
| 分发凭据与私钥同等敏感 | SourceForge 上传账号或 SSH key 泄露后，攻击者可替换已发布文件。哈希不匹配会拦住安装，但仍需按分发源被入侵处理并重发 |
| 渗透测试未做 | 属人工工作 |

警告：激活第三方界面前，确认文案须写明“启动器无法验证界面内容”。不披露时，仿冒的配置页可能诱导用户输入密钥。

## 不在范围内

- 上游各模块自身的漏洞，提交到各模块仓库。
- 宿主机层面的攻击。
- 进程沙箱。本版只做披露，不声称隔离。

## 出网边界

启动器自身的 HTTP 客户端受已配置下载源约束。该约束不作用于启动器拉起的子进程。三个上游由独立进程运行，出网行为由各自配置决定，启动器不代理、不拦截。

因此“启动器不出网”不等于“上游也不出网”。要让输入、模型、语音三层都离线，需逐个改用本地厂商，并预置 Python 运行时与 wheels。

## 密钥归属

密钥由各模块自己保管。启动器与 Dounai 悬浮窗都不保存密钥副本，也不把密钥注入子进程环境变量。

签名密钥是另一回事。K1 私钥在仓库外离线保管，启动器只内置 K1 的公钥指纹。用这把私钥签出的包按已信任处理。生成、保管与轮换规程见 [docs/SIGNING.md](docs/SIGNING.md)。

| 层 | 密钥位置 | 读取方 |
|---|---|---|
| 输入层 | 模块根 `.env` | 输入层自己 |
| 语音层 | 模块根 `.env` | 语音层自己 |
| 模型层·内置厂商 | 模块根 `.env` | 模型层自己 |
| 模型层·自定义厂商 | SQLite 的 AES-GCM 密文 | 模型层自己，对外只返回掩码 |

启动器只读写“该变量是否已配置”的布尔状态，不读值、不回显值，写完后即丢弃。密钥集中在一处时，轮换与审计只需看一个地方。启动器即使被替换，也拿不到密钥。

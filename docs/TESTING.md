# 测试补充说明

> 记录启动器测试过程中发现的、**容易让测试本身失效**的两个陷阱。
> 这两条不是产品缺陷，但会让"测试通过"变成假象。

---

## 1. 增量编译缓存导致测试结果失真（已实测复现）

### 现象

我在做「变异测试」（故意注入缺陷，验证测试能否抓住）时遇到：

1. 注入缺陷 → 测试失败 ✅（符合预期）
2. 还原代码 → **测试仍然失败** ❌（不符合预期）
3. 再次注入 → 测试失败
4. `cargo clean -p dounai-launcher` 后 → 测试通过 ✅

### 根因

`security.rs` 被还原后，**增量编译没有重新编译该库**，测试链接的仍是注入缺陷后的旧 `rlib`。

清理时移除了 4.1 GiB 构建产物，之后行为立即恢复正常。

### 影响

- 变异测试的结论会变成**假阳性**（以为测试抓住了缺陷，实际只是旧产物在作祟）
- 更危险的对称情况：修好缺陷但测试仍失败，或注入缺陷但测试通过，都可能被误读

### 应对

**做变异测试或修改安全关键代码后，必须清理构建产物再验证：**

```powershell
cargo clean -p dounai-launcher
cargo test --all-targets
```

CI 里每个 job 都是干净环境，不受此影响；但在本地做这类验证时容易踩坑。

## 2. 断言过弱会让"防线退化"被掩盖

### 现象

`fuzz_safe_join_never_escapes_destination` 只断言「被接受的路径必须仍在目标目录内」。

当我删掉 `safe_join` 里 `ParentDir` 的显式拒绝后，**这条测试仍然通过**——
因为末尾的「包含性复核」把越界兜住了，结果依然安全。

### 为什么这是问题

纵深防御的价值是双保险，但**不能因为第二道还在就默许第一道失效**。
一旦有人误以为「有兜底就够了」而删掉前置检查，防线就悄悄少了一层，
而测试不会报警。

### 应对

新增 `fuzz_attack_strings_are_explicitly_rejected_by_design`：
要求攻击串返回**语义明确的错误类型**（`Traversal` / `Absolute` / `ReservedName`），
而不是"随便报个错就算过"。

验证：注入缺陷后这条会准确失败，而其余 7 条仍通过——说明它确实在守那道具体的防线。

## 3. fuzz 的实现方式与覆盖范围

`tests/fuzz_invariants.rs`，8 项测试，约 4300 次迭代。

| 不变量 | 覆盖方式 | 迭代数 |
|---|---|---|
| `safe_join` 不越界 | 结构化变异（拼路径池片段 + 随机分隔符 + 随机字符） | 2000 |
| 攻击串按设计拒绝 | 显式枚举 14 个真实攻击串 | 14 |
| 解压不越界/不 panic | 纯随机字节直接喂给 zip 解析与解压 | 300 |
| 恶意条目整体拒绝 | 14 个恶意条目各构造一个混合包 | 14 |
| 正常条目不被误拒 | 5 个正常路径反向验证 | 5 |
| 清单解析不 panic | 随机字节 | 500 |
| 清单结构化变异 | 以真实清单为基底做翻转/截断/插入 | 300 |
| base64 解码不 panic | 随机可打印字符 | 800 |

### 为什么不用外部 fuzz 引擎

- 无需 nightly 与额外工具链，CI 直接可跑
- **种子固定**（`0xC0FFEE`、`0xDEADBEEF` 等），失败可复现
- 覆盖的是真实攻击面（zip 头、路径字段、JSON 结构），而非纯随机噪声

代价：不追求覆盖率最大化，只保证**已知攻击面**的不变量成立。
真正的覆盖率引导 fuzz 属于后续可选项。

### 反向验证

fuzz 最常见的失败模式是「全部拒绝」也能通过。
因此专门有一条 `fuzz_good_entries_still_accepted`，
确保正常路径不被误拒。

## 4. 复现命令

```powershell
cd src-tauri

# 全部测试
cargo test --all-targets

# 只跑安全不变量
cargo test --test fuzz_invariants

# 做变异测试时（必须先清理）
cargo clean -p dounai-launcher
cargo test --test fuzz_invariants
```
